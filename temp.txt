What's wrong with the current flow:
Right now Agent 3 (VizMeta) and Agent 4 (PlotlyCode) always run after every query. So a query like "how many ULBs are in Maharashtra?" returns a bar chart of 1 number — which is useless. Or "list all questions in the survey" returns a chart of 200 text rows — also useless.
What you're proposing — and I fully agree:
After SQL executes and result lands, instead of blindly running viz agents, add a new step:

Agent 2.5 — Answer Framer (new LLM call, small and fast): looks at the SQL result and writes a natural language answer like "There are 47 ULBs in Maharashtra across 6 districts." or "The top district by maturity level is Pune with an overall score of 4.2." This replaces the empty space between result and chart.
Chart feasibility check (can be part of the same agent or separate): the agent also decides — is this data chartable? Returns chart_feasible: true/false and a reason like "Single scalar value — no chart meaningful" or "10 rows with 2 columns — bar chart recommended".
User confirmation prompt: UI shows the framed answer + a minimal inline prompt: "Want to see this as a chart?" with Yes / No buttons. If the data isn't chartable, the No button is pre-selected with the reason shown.
Conditional Agent 3+4: only fires if user clicks Yes.

The flow becomes:
SQL result → Answer Framer Agent → framed_answer + chart_feasible + reason
                                 → SSE: answer_ready event
                                 → UI shows answer + Yes/No prompt
                                 → User clicks Yes → SSE: chart_request
                                 → Agent 3 (VizMeta) → Agent 4 (Plotly)
                                 → User clicks No → done, pipeline ends
What changes in which files:
nl_to_sql_main.py — new AnswerFramerAgent class with its own prompt, inserted between validator and VizMeta. stream_query() yields a new answer_ready SSE event and then pauses — it needs to wait for user input before continuing to viz agents.
app.py — new route POST /query/continue that accepts {request_id, proceed_with_chart: true/false} and resumes the pipeline. This is the tricky part — the generator needs to be held in memory between the pause and resume.
sarthi_index.html — new answer_ready SSE handler that renders the framed text answer and shows Yes/No buttons. Yes button calls /query/continue, No button just closes the stream.
The hard architectural problem:
Pausing a Python generator mid-stream and resuming it from a new HTTP request is non-trivial. The cleanest approach is a queue-based handoff:

When answer_ready fires, the generator puts itself into a dict keyed by request_id and blocks on a threading.Event
The /query/continue route looks up the request_id, sets the event with proceed=true/false, and the generator resumes

This is production-safe, works with Flask's threaded server, and doesn't require websockets.
